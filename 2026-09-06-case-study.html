Max Prescott, September 2026. Every figure here is measured from the folder the agents run in. Where a number depends on a counting rule, the rule is stated next to it.

On 8 August I gave a set of Claude agents a folder on my desktop and nine scheduled jobs. Between 1:30am and 4am they read my email, put my cafe roster on the calendar, chase the bills that are due, keep a ledger of what I've committed to, maintain a written model of me, and write a brief that is waiting when I wake at five. In the evening one of them asks me three questions about the day. That's the whole system, and I want to be precise about it because "agents running my life" is the kind of line that makes an engineer look for the exaggeration instead of the result.

Over the 29 days after 8 August the folder accumulated 487 log entries, 240 knowledge nodes and 63 small tools. It also accumulated a record of 125 documented failures, which I'll define in a moment, of which I personally found 34 and automated checks or a second agent found the other 91. I'm not an engineer. I run a cafe north of Brisbane and finished a finance degree in August. What I brought was a habit of writing down what broke and refusing to fix it twice by hand, so the folder now has a smoke test that prints its own count of checks every run, no file is permitted to state that count, and every check exists because a specific thing went wrong. That last part is a weakness as much as a method: it's regression coverage, not proof the system is safe, and a class of failure that hasn't happened yet has no check. I'll come back to that.

The counting rule and the denominator

A failure is one row in a catalogue built from four places: the reason line on each check in the smoke test, the twelve rows of an interventions ledger that records every time I did a job the agent should have done, a retired-claims file that holds every belief about me that was later disproven with the evidence that killed it, and log entries that name a wrong action. A recurrence of the same bug on a later day is a separate row if it was documented separately, which means 125 leans high rather than low. Correlated failures are marked as such in the catalogue.

The denominator the folder can give you is this: since 19 August, when the jobs started writing their own step-state, there have been 81 recorded scheduled runs made of 242 recorded steps, 23 morning briefs sent, and 487 log entries written. I can't give you a count of "meaningful operations" and I'm not going to invent one.

Two-thirds of the log is about building the system rather than about me. A separate Claude session with fresh context audited the folder on day eight and put the figure at 85% at that point, and the share fell as the system settled and the two numbers are dated, not competing.

What the failures were

By category, with the count in the catalogue: stale state and stale numbers, 14. Silent skips and green boards over nothing, 21. Prompt and mirror drift, 8. Concurrency, allocation and provenance, 15. Reading me wrong, 12. Invented facts and words put in my mouth, 9. Corrections over-applied and defects introduced while fixing, 21. Deliverables with figures that verification structurally can't catch, 13. Cost, quota and runaway, 12.

I expected hallucination and there was some. What there was far more of was the agent being confidently right about a thing that had stopped being true.

Stale state reported green. The file every agent reads first is a one-page summary of my current situation. On day five the check that verified it was current was measuring the file's modification time, and something had touched the file, so it passed while the header said 9 August and the date was the 13th. The fix was to parse the date and then measure it against the log the summary is built from rather than the header the same job writes. Verify the outcome, not the artefact. The folder has relearned that at least five times.

Numbers in documents that nothing measured. The instructions file told every session that a particular tool cost about 400 tokens to run. It cost 1,287. It had been typed once and never measured again. The fix isn't magic and I should say exactly what it is: a check that scans a fixed set of documents for a small grammar of claims, ~N tokens, N entries, N tools, N passed, a stated clock time next to a named job, and re-measures each one against the thing it names. It can't verify "six days" or "85%". Within an hour of widening it from one file to that grammar it found nine wrong times in the README, a task table two rows short, and a feature described as live six days after I'd killed it.

Checks that passed on nothing. On day six an audit found four checks passing vacuously, including a budget check that got greener when the file it measured was missing, because a missing file scored zero. Now every check declares a minimum population, and a check over fewer items than that fails. That prevents one class of empty-input pass. It does not prove the check is measuring the right thing.

Silent skips. This is the one that worries me most for anyone running agents on a schedule. A nightly step that swept my summary for contradictions gated itself off for fourteen nights because a token budget was slightly over its cap. It recorded the skip correctly every night. Nothing read the record. The board stayed green while the one file every session opens first went unchecked for two weeks. Separately, the evening job fired one night, printed "No response requested", asked me nothing, and the whole night's collection depended on me noticing it hadn't. I typed "rerun didnt work" the next morning. A step that skips itself now warns at one night and fails at eight, and a job that can end without its primary artefact has to declare that as a state.

A layer nothing routed to. The first knowledge base was a graph of 141 nodes, 66 of them junk, and it died twelve days in because its rebuild had never been put in any prompt and nobody read it. A human noticed. Nothing else could have, because no job had a path to that folder.

Prompt drift. The folder was reorganised on day six. The routing table was updated and nothing else was, so three of six scheduled prompts pointed at dead paths for two days, including the evening job's close-out, which is the system's main way of learning that something is done. Going the other way, a session edited the mirror copies of two prompts instead of the live ones, and the 4am job overwrote the edits from the live copies and said nothing. Mirror drift is now a recurring nightly finding, five times in the log so far.

Two writers, one number. For the first five days two agent sessions were each computing "the next entry number" and appending, so the log had 62 headings and 46 distinct numbers, with 14 reused. The model of me cites evidence by entry number, so the citation graph had quietly stopped resolving. The fix is one script that allocates under a file lock and opens the file in append mode, and nothing else may write. Later, a session chained a knowledge-base write onto the append with && and cited the number it assumed would be allocated. Twelve entries had landed from other threads in between, two edges pointed at another job's work, and nothing about the result looked wrong. I did the same thing myself while writing this piece and caught it on the read-back.

Reading me wrong. The model claimed my days had last had external structure in 2019. I competed in a card game at national and international level through 2024. The claim was off by five years because it had been written once with a figure in it and never evidenced. The knowledge base held one family member as two separate people, created a day apart by two different jobs, with the same opening line in both summaries. And one record read me higher than the truth rather than lower: a session tidying a CV replaced a job title with a more generic one, which removed the only word naming a formal traineeship and cost four weeks of not knowing. That one came from tidying an artefact rather than reasoning about me.

Things put in my mouth. A cover letter described my job using a phrase lifted from my own GitHub pull request titles, and I couldn't parse it when I read it. A voice guide quoted a sentence back to me as something I'd written, and an agent had drafted it, and it had been live in two letters and instructed for reuse since. Every quotation attributed to me now carries its origin in the sentence: said, sent, or drafted, and only "said" with an entry number counts as evidence of how I write.

Figures that tracing can't catch. A cover letter joined a food-cost percentage, measured on 28 dishes and a known slice of sales, to a much larger annual sales figure in one sentence, implying a denominator it never had. Three verification passes had traced every figure to a source and all three passed, because each figure was true. When two figures share a sentence, name the basis of each.

Over-applied corrections. I said "less analytical" about one section of the brief and the subject got removed along with the metrics. I said "no instructions" and the position got removed along with the task. I said the voice was too choppy, and a session cut function words to hit a word budget until the sentences read as if words had been removed, which they had. When I correct one dimension the agent changes that dimension only, and getting that into a rule took three separate instances.

Cost. Two research subagents were killed mid-run by a monthly spend limit and nobody was tracking parallel cost at all. Three nights in a row were missed on a usage limit, and the system recorded the symptom in three places while having nowhere to record the one-line cause. The log file itself is now past 355,000 tokens and past its own runaway line, and that's an open red line on today's board.

What caught them

Thirty-four were me. Of the other 91, nearly all were caught by a check written after a failure of the same shape somewhere else, which is the finding I'd put above the others: a lesson gets applied at the site where it was discovered and is never swept for other instances of the same shape. On day eight the fresh-context audit found eight defects, and every one was a shape that had already been diagnosed once: a number in prose that nothing verifies, a second copy of owned data, a hand-allocated id, an entity with no canonical name. The response was four checks that sweep for the shape rather than the instance.

The other line the folder keeps relearning is that a rule an agent is asked to follow is a suggestion, and a rule it can't break is a mechanism. "People are things about his life, give them nodes" was written into two skills. Two days later there were 37 nodes and none of them was a person. It took a check that fails the board when a person is mentioned and not noded before it happened.

What it was like to use

I was asked this properly for the first time tonight, so here it is in plain terms. I use all of it, every day: the brief, the evening questions, the ledgers and the chases, and threads where I ask it things. It changed something real in 29 days, but not the thing it was built for. It was meant to make my days run better. What it actually did was teach me to build systems that keep agents honest, and that turned out to be the more valuable thing.

The five defects I'd name, as the user rather than the builder. It's slow. It runs on my Mac, so the Mac has to be on. The brief often states the obvious, because it can't see what I'm reading and learning between entries, so its picture of my subjects lags mine. The chaser only ever chases dates I gave it, and it never looks at a subject slipping and invents a due date to stop the slide, which is the thing I'd want most. And the brief struggles to get outside its own folder: it can spot a pattern in what's recorded and can't carry it to an idea that lives outside the record. Three of those five are now changed as a result of being asked: every chase starts closer to the date, the chaser can invent a dated row from a subject going quiet, and the brief searches the web on my live subjects each night. The other two are an input problem and a hosting problem, and both are on the board.

What watchman is, and what it isn't

I pulled twelve checks out of the folder into a small standalone tool, stdlib Python, one watchman.toml in the folder being watched. Trace systems tell you whether a run behaved correctly. Watchman checks whether the durable state the next run will trust is still valid. That's the distinction, and it's narrower than "nobody does this": LangSmith, Braintrust, Langfuse and Arize all let you attach custom evaluators to production traces, and a competent engineer could rebuild most of these twelve with them. What they organise around is runs, traces and spans, so they need the agent to emit telemetry. Watchman reads the files.

It does not work over "any folder of agent state". It works over file-backed agents that follow the conventions the toml describes: a read-first summary with a marker line naming its source, ledgers with declared closed sets, jobs that write a step-state file, prompts kept in a mirror directory, citations in the form E123. Six of the twelve checks are generic given those conventions: stale state, degraded steps, prompt drift, closed sets, append-only log, read budget. Six are opinions from my folder that you may not share: stated-vs-measured, the no-vacuous-pass floor, the intervention tally, absence against cadence, citations that resolve, and written-down cannots with a re-test date. The README says which is which and shows the toml, the fixture, a board, and the exit codes. The code, this piece, the board over my own folder and the prospective ledger are at github.com/maxprescott02-source/Watchman.

I ran it over the folder it came from before writing this. The board came back mixed, and two of its red lines were things the folder's own smoke test had never reported: a second dead path in the weekly maintenance prompt, and eight duplicate entry numbers in the August log that had been sealed rather than corrected. A tool built from a system's failures found two more in the system on its first run, which is the most useful thing I can tell you about it.

And it's retrospective evidence. Failure happened, check got written, similar failure got caught. That's the weakest kind. So the next step is fixed before this goes out: watchman is frozen at this version and runs unchanged over the folder for the 28 days to 5 October, and I'll publish the result as a confusion matrix, true positives, false positives, failures it missed, and checks that never fired. If the missed column is long, that's the finding.

Five lines of the board are red as I write this, and I know which five and why. That's the state I'd want you to aim for: not a green board, a board you can read.

The twelve checks

  1. stale-statethe summary agents read first is measured against its source, never its own date
  2. stated-vs-measuredevery number stated in a document is measured on every run
  3. no-vacuous-passevery check declares a floor; a check over nothing fails
  4. degraded-stepsa scheduled step that skips itself is visible at one night and red at eight
  5. prompt-driftprompts point at paths that exist and mirrors match the live copies
  6. closed-setsledger states are a closed set; Noted is not an outcome
  7. intervention-tallyevery time you did the agent's job is a row, and the rate is the measure
  8. absenceanything gone quiet against its own cadence is reported
  9. append-only-logone writer, one lock, monotonic numbers
  10. citation-resolvesevery E-number in the knowledge base resolves to an entry
  11. cannot-listevery written-down cannot carries a re-test date
  12. read-budgetfiles opened whole are capped, and growth past the line fails

Stdlib Python, no dependencies, one watchman.toml in the folder you want watched. watchman init writes a starter config and the demo. watchman report prints the board and exits non-zero on red. watchman heartbeat is for the second runner, so the checker is itself checked.
